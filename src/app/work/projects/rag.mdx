## Overview

Traditional study of the Vachanamrut requires manual navigation across multiple chapters, contexts, and philosophical explanations. While rich in wisdom, extracting precise answers to specific questions can be time-consuming—especially for students, speakers, and seekers exploring thematic understanding.

To address this, I built an **AI-powered Retrieval-Augmented Generation (RAG) chatbot** trained on the Vachanamrut, enabling users to ask natural-language questions and receive contextually grounded answers sourced directly from the scripture.

The project was designed as a **self-hosted, explainable, and scalable AI system**, with a strong emphasis on faithfulness to the original text rather than generic LLM responses.

# Technical Deep Dive (Architecture & Design Decisions)

This section dives deeper into the technical implementation of the Vachanamrut RAG Chatbot for readers interested in system design, trade-offs, and AI engineering details.

## High-Level Architecture

The chatbot follows a standard **RAG pipeline**, separating knowledge retrieval from language generation.

**Flow:**

1. User submits a question through a web UI
2. The query is converted into an embedding
3. A vector database retrieves the most relevant scripture passages
4. Retrieved context is injected into a grounded prompt
5. A Large Language Model generates the final response

> The LLM is used only for response synthesis — all domain knowledge is retrieved externally.

---

## Data Source

The raw Vachanamrut text was sourced from [**Anirdesh.com**](https://www.anirdesh.com/vachanamrut/index.php?format=en), a publicly accessible digital archive.  
The data was used solely for educational and non-commercial purposes.

Before indexing, the text underwent:

- Cleaning and normalization
- Structural segmentation by discourse
- Metadata enrichment (chapter, reference number, titles)

---

## Text Chunking & Indexing Strategy

The Vachanamrut text was segmented using a **fixed-length, overlap-based chunking strategy** implemented via a recursive character splitter.

Trade-offs Observed

- During testing, I observed the following trade-offs:
- Some philosophical explanations span multiple chunks, requiring overlap to preserve meaning
- Larger chunk sizes improved contextual completeness but reduced retrieval precision
- Smaller chunk sizes increased recall but sometimes fragmented ideas

Key considerations:

- Balanced chunk size for retrieval accuracy and context completeness
- Avoiding fragmentation of explanations across chunks
- Preserving metadata for traceability and source attribution

Each chunk was independently embedded and indexed.

---

## Embeddings

Text embeddings were generated using a **sentence-level embedding model** optimized for semantic similarity tasks.

Important design decisions:

- The **same embedding model** was used for both document indexing and query embedding
- Embeddings were normalized to improve cosine similarity matching
- No domain fine-tuning was applied to avoid overfitting

---

## Vector Database & Semantic Retrieval

For semantic search, I used **FAISS (Facebook AI Similarity Search)** as the vector database.

FAISS enables:

- Efficient similarity search over dense embeddings
- Fast top-K retrieval at query time
- Local, lightweight deployment without managed infrastructure

At runtime:

- The user query is embedded
- FAISS retrieves the top-K most semantically relevant Vachanamrut passages
- Retrieved chunks are passed downstream for grounding

---

## Prompt Engineering & Grounding

To minimize hallucinations, the system enforces **strict grounding rules**.

The prompt explicitly instructs the LLM to:

- Answer **only** from the provided Vachanamrut passages
- Avoid adding external interpretations or assumptions
- Respond concisely and respectfully

If the retrieved context does not contain an answer, the system responds with:

> “This is not mentioned in the Vachanamrut.”

This constraint significantly improves reliability and trustworthiness.

---

## Language Model

A Large Language Model (LLM) is used exclusively for **language generation**, not knowledge storage.

Design principle:

> The model should not “know” the Vachanamrut — it should **read it at runtime**.

This keeps the system:

- Stateless
- Auditable
- Resistant to hallucinated knowledge

Generation parameters (temperature, token limits) are tuned to favor accuracy over creativity.

---

## Conversational Context Handling

The chatbot supports multi-turn interactions using a **limited rolling conversation window**.

Implementation notes:

- Recent user queries and responses are appended to the prompt
- Context length is capped to prevent retrieval dilution
- Long-term memory is intentionally avoided

Through experimentation, I observed that excessive conversational memory can negatively impact retrieval relevance — highlighting a key trade-off in RAG system design.

---

## User Interface

A lightweight web interface built using **Gradio** allows users to:

- Ask natural language questions
- View answers alongside exact source passages
- Adjust generation parameters for experimentation

The UI is intentionally minimal, prioritizing clarity and traceability over visual complexity.

---

## Deployment

The chatbot is deployed publicly using **Hugging Face Spaces**, enabling:

- Easy sharing
- No local setup for users

---

## Design Decisions & Trade-offs

- **FAISS over managed vector DBs**: simplicity and local control
- **Strict grounding** over fluent responses
- **Limited memory** to preserve retrieval accuracy
- **No fine-tuning** to maintain interpretability

These decisions were driven by correctness, not demo aesthetics.
